# 工具小程序设计示例

> 示例性质：展示“打开即用”的工具型小程序设计。

## 需求

- 产品：工具应用小程序
- 技术栈：微信原生
- 核心任务：输入/选择 → 得到结果 → 复制/分享/保存 → 查看历史
- 用户：有明确任务的个人/职场用户
- 风格：未指定


## 设计重点

工具型小程序的价值是“少步骤完成任务”：

1. 打开即看到输入/工具；
2. 输入和结果关系清楚；
3. 结果可复制/分享/保存；
4. 失败可恢复；
5. 历史可查，但不是首页主角。

品牌故事、活动 banner、四宫格服务入口通常都不应出现在首屏。

## 首页

- 直接的工具输入或最近使用；
- 需要多工具时用清晰列表，不用彩色宫格堆满；
- 设置/历史放在次级；
- 只有存在 3 个以上稳定一级区域时才考虑 TabBar。

## 结果

- 结果与输入上下文关联；
- 复制按钮有成功反馈；
- 分享真实可用；
- 结果支持长文本/大数字；
- 失败说明原因和重试。

## 视觉

- 黑白/中性底；
- 一个品牌色用于主操作和焦点；
- 少量边框/间距建立结构；
- 按钮高度足够；
- 结果区域清晰，不用卡片套卡片；
- 动效只用于计算/复制状态。

## 状态

- 输入校验；
- 计算中；
- 结果；
- 空结果；
- 错误与恢复；
- 复制成功；
- 历史为空。

## 应避免

- 先放品牌故事；
- 死按钮；
- 输入/结果相隔很远；
- 全屏 loading 遮住返回；
- 结果不可复制；
- 用大量渐变填充极简布局。

## 技术栈注意

- 原生 WXML/WXSS；
- 输入用 input/textarea，不用 view 模拟；
- 复制使用 `wx.setClipboardData`（按目标基础库）；
- 长文本输入处理键盘；
- 固定结果/操作栏加安全区；
- 本地历史注意隐私和清理。

## 验证边界

- 未实现具体工具算法；
- 未运行小程序；
- 未验证复制、键盘、长文本和安全区；
- 未测试低端机性能。

工具产品的正确性主要由业务算法和输入验证决定，视觉系统不能替代它们。

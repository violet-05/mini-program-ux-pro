# 小程序设计原则

## 设计不是一种固定气质

“高级感”不是一个可以套用到所有产品的视觉滤镜。对金融产品，高级可能是秩序、透明和可信；对音乐产品，高级可能是封面、播放状态和内容节奏；对智慧农业，高级可能是强光下仍能读清的数据和大触控区。设计方向必须从业务目标、用户场景、平台约束和品牌资产推导。

MPUX Pro 用一条简单链路约束设计：

```
产品任务 → 用户场景 → 页面结构 → 信息层级 → 视觉语言 → 交互状态 → 平台适配 → 验证
```

颜色和阴影永远在链路后段，而不是起点。

## 原则 1：任务优先

每个页面先回答“用户来做什么”，再决定长什么样。首屏应让一个主任务清楚可见。次要入口、活动和推荐不能把所有东西做成同一权重。

可操作方法：

- 为每个首屏模块写一句目的；
- 标出唯一主操作；
- 删除没有用户价值的装饰模块；
- 用灰度截图复查层级。

## 原则 2：清晰胜过惊喜

用户不应该猜：

- 当前在哪；
- 点这个会发生什么；
- 为什么失败；
- 下一步怎么恢复；
- 数据是否保存/支付是否成功。

导航、按钮、表单、订单状态和错误说明必须用直白语言。视觉惊喜只能在不增加理解成本的地方出现。

## 原则 3：平台不是浏览器

微信小程序有自己的导航、路由、TabBar、生命周期、原生组件、权限和验证环境。WXML 不是 HTML，WXSS 不是完整浏览器 CSS，模拟器不是真机。

设计时必须明确：

- 技术栈是原生、uni-app 还是 Taro；
- 页面在哪个渲染引擎/基础库运行；
- 哪些能力需要真机验证；
- 哪些代码只是浏览器原型。

详见 [小程序平台](mini-program-platform.md) 与 [兼容性说明](../docs/compatibility.md)。

## 原则 4：状态是设计的一部分

仅有成功态的页面不算完成。设计应覆盖：

- 首次加载；
- 局部刷新；
- 空数据；
- 搜索无结果；
- 无权限/未登录；
- 失败与重试；
- 弱网；
- 键盘；
- 重复提交；
- 长文本；
- 图片失败；
- 深色模式。

这些状态比“卡片好不好看”更直接决定体验。

## 原则 5：一致性不等于同质化

一致性指：

- 同一语义同一种颜色；
- 同一层级同一种字号；
- 同一动作同一种反馈；
- 同一组件同样的状态；
- 圆角、边框、阴影来自同一语言。

同质化指所有产品、所有页面都使用同样的搜索框、轮播、四宫格和卡片。前者是系统，后者是模板。我们需要系统，不需要模板。

## 原则 6：可访问性是底线

- 正文和背景至少 4.5:1；
- 触摸目标至少 88rpx×88rpx（并参考官方 7–9mm 建议）；
- 不只靠颜色表达状态；
- 支持系统字号；
- 表单有持续可见标签；
- 错误可定位；
- 动效可以降级。

详见 [可访问性](accessibility.md)。

## 原则 7：克制的差异化

差异化来自：

- 针对业务的内容顺序；
- 独特的图像/排版/色彩资产；
- 适合场景的密度；
- 品牌语气与交互反馈；
- 真正被设计过的状态。

不是来自：

- 每个页面都放渐变；
- 所有按钮都变胶囊；
- 所有卡片都加大圆角和阴影；
- 用 Emoji 当图标；
- 用装饰动效掩盖结构问题。

没有理由的选择，默认视为模板化风险。

## 设计完成前

- [ ] 页面任务清楚；
- [ ] 状态完整；
- [ ] 触摸与对比度达标；
- [ ] 安全区和键盘处理明确；
- [ ] 技术栈没有混用；
- [ ] 验证环境记录；
- [ ] 未执行项没有被说成通过。

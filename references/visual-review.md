# 视觉审查

## 先声明环境

视觉结论依赖环境。审查报告必须写明：

- 静态代码 / 浏览器 / 开发者工具 / iOS 真机 / Android 真机；
- 设备尺寸/系统/微信版本/基础库；
- 页面状态；
- 是否加载真实数据。

静态代码无法验证实际视觉；模拟器不能代替真机。

## 审查前准备

- 设计系统 Master；
- 页面清单与核心任务；
- 目标用户/场景；
- 截图或运行环境；
- 已知限制；
- 不改变的业务逻辑。

## 审查顺序

1. **任务**：首屏是否围绕核心任务。
2. **层级**：第一眼看到什么，是否正确。
3. **结构**：区域/顺序/固定操作。
4. **状态**：加载/空/错误/键盘/权限。
5. **排版**：字号/行高/长文本。
6. **色彩**：对比/语义/深色。
7. **间距/对齐**。
8. **图片/图标/组件**。
9. **动效**。
10. **模板化风险**。

颜色调整放到任务和结构之后。

## 证据

每个问题应有：

- 页面/状态；
- 设备/环境；
- 截图或代码位置；
- 可观察事实；
- 影响；
- 修复；
- 判断方式（自动/规则辅助/人工/视觉模型）；
- 置信度。

不要只给“感觉不够高级”。

## 可量化项

- 对比度；
- 字号；
- 触摸热区；
- 固定底栏/安全区；
- 文本溢出；
- 图片比例；
- token 一致性；
- 首屏是否包含主任务。

审美项（风格匹配、节奏、品牌）可以评审，但要说明是判断而不是测量。

## 视觉模型接口

当前未内置视觉模型。`scripts/visual_review_adapter.py` 定义了请求/响应契约、校验函数与不可用适配器；它不调用模型或网络。适配器输出必须符合：

```json
{
  "issue": "首屏主任务被活动横幅挤出",
  "severity": "P1",
  "evidence": "390×844 截图中购买按钮位于第二屏",
  "suggestion": "活动区下移，主操作进入首屏",
  "confidence": 0.86
}
```

模型结果与程序测量分开。模型不替代真机或业务判断。

## 评审问题清单

- 页面像不像通用模板？
- 首屏有没有唯一焦点？
- 主操作是否明显？
- 信息密度与任务匹配吗？
- 所有模块是否同一种卡片？
- 颜色有业务理由吗？
- 深色模式可用吗？
- 长文本/价格/标题会破吗？
- 底栏/键盘安全吗？
- 空/错状态是否也经过设计？
- 品牌和产品类型匹配吗？
- 有没有只改颜色？

## 报告格式

按 P0–P3 分组；每个问题给证据。最后列出：

- 已检查页面/状态；
- 未检查；
- 环境；
- 需要产品/品牌决策；
- 建议的下一轮。

## 禁止

- 没有截图却评价像素；
- 用“高级/低端”代替可执行建议；
- 只给审美分；
- 将浏览器效果当小程序真机；
- 把未执行检查写成通过。

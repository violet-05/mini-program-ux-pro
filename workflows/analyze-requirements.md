# 需求分析工作流

## 目标

在写页面或设计系统之前，先确定产品任务、用户、技术栈和验证边界。避免“看起来像小程序”的模板化设计。

## 输入

用户可能只给一句“帮我把这个电商小程序做高级一点”。不要立刻改颜色或开始写页面。先收集以下事实：

| 维度 | 需要知道 | 来源 |
| --- | --- | --- |
| 技术栈 | 微信原生 / uni-app / Taro | 项目 `project.config.json`、`app.json`、`pages.json`、`package.json`、`app.config.*` |
| 产品类型 | 电商、内容、工具、数据、服务等 | 用户描述 + `data/products.csv` 检索 |
| 核心任务 | 用户来做什么、完成后什么算成功 | 页面、导航、现有业务 |
| 目标用户 | 年龄、场景、设备、网络、能力差异 | 用户说明与项目内容 |
| 品牌方向 | 已有品牌资产、指定风格、禁忌 | 用户说明与现有资源 |
| 页面范围 | 要改哪些页面、哪些保持不动 | 用户明确授权 |
| 验证环境 | 静态 / 浏览器 / 开发者工具 / 真机 | 实际可用工具 |
| 交付形式 | 只建议 / 改代码 / 设计与审查报告 | 用户明确要求 |

## 步骤

1. **读取项目，不先改代码。** 识别技术栈、页面注册、组件库、样式 token、现有业务逻辑。
2. **提炼一个主任务。** 例如“音乐播放器”的主任务可能是继续播放与发现，不是营销首页。
3. **列出已有约束。** 不能改变的路由、支付、登录、数据和业务逻辑。
4. **检索产品类型与设计推理。**
   ```bash
   python scripts/search.py "音乐播放器 内容发现 持续播放" --domain product -n 3
   python scripts/search.py "内容消费 播放状态" --domain reasoning -n 3
   ```
5. **判断风格缺口。** 用户指定风格则尊重；没有指定时先看产品推荐，而不是默认极简。
6. **形成需求摘要。** 使用下方模板，并请用户确认真正影响方向的事项。不要为字号、圆角等细节反复打断。
7. **冻结范围。** 明确哪些页面/组件会改，哪些不改；哪些验证会执行。

## 需求摘要模板

```markdown
# 需求摘要

- 项目：
- 技术栈：
- 产品类型 / 检索记录：
- 目标用户：
- 核心任务：
- 次要任务：
- 页面范围：
- 不改变的业务：
- 用户指定风格：
- 信息密度：
- 关键状态（加载/空/错误/权限/支付）：
- 验证环境：
- 交付物：
- 明确不做：
```

## 输出

- 一份可执行的需求摘要。
- 检索到的产品/风格/推理记录 ID。
- 尚未确认的事实与假设。
- 如果用户只要建议，到此停止，不改文件。

## 禁止

- 未读项目就假设它是微信原生。
- 把所有小程序都设成同一种“高级感”。
- 把 H5/浏览器原型当作已验证的小程序。
- 用模糊的“优化体验”代替可检查的问题。

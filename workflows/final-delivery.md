# 最终交付工作流

## 目标

让用户准确知道：改了什么、为什么、在哪些环境验证、哪些还没验证、下一步是什么。

## 1. 交付前核对

- [ ] 用户要求范围内的工作已完成。
- [ ] 没有删除或改写未授权的业务逻辑。
- [ ] 设计系统/页面覆盖与代码一致。
- [ ] P0 为零，P1 已修复或有明确阻塞原因。
- [ ] 静态审查已重新运行。
- [ ] 代码可编译（在可用环境中）。
- [ ] 未执行的环境已明确列出。
- [ ] 没有密钥、AppSecret 或隐私数据进入交付物。

## 2. 环境矩阵

| 环境 | 已执行 | 证据 | 未执行原因 |
| --- | --- | --- | --- |
| 静态代码审查 |  |  |  |
| 浏览器预览 |  |  |  |
| 微信开发者工具 |  |  |  |
| iOS 真机 |  |  |  |
| Android 真机 |  |  |  |
| 弱网 |  |  |  |
| 视觉模型 |  |  |  |

不要在一个模糊的“已验证”里合并这些环境。

## 3. 交付内容

至少包含：

1. **变更摘要**：修改了哪些页面/组件/设计系统。
2. **设计依据**：产品、风格、配色、布局和规则的数据 ID。
3. **修复清单**：问题 ID、严重度、处理结果。
4. **修改文件**：列出路径和用途。
5. **验证记录**：环境、步骤、结果。
6. **未完成项**：问题、原因、下一步。
7. **风险**：可能影响业务或需要产品确认的事项。
8. **运行方法**：如何安装、生成、审查、回滚。

## 4. 报告格式

使用 [审查报告模板](../templates/review-report.md)。如果有设计系统，附：

- Master 路径；
- 页面覆盖路径；
- token 文件；
- 生成时间/版本；
- 与上版差异。

## 5. 不得声称

- “已全部验证”但没有真机记录。
- “已通过微信验证”但只在开发者工具看过。
- “可访问性通过”但没有检查对比度/读屏/触摸。
- “性能已优化”但没有测量。
- “设计已重构”但只换了颜色。
- 把视觉模型的主观判断称为客观测量。

## 6. 交接给下一个维护者

写下：

- 先读哪个 Master；
- 哪些页面有覆盖；
- 哪些平台规则必须真机验证；
- 哪些数据记录是设计来源；
- 哪些问题被有意留下；
- 如何运行验证；
- 回滚点/分支（如适用）。

## 7. 最终声明模板

```markdown
## 完成情况

- 已实现：
- 已修复：
- 已执行验证：静态审查、…
- 未执行验证：微信真机、键盘、视觉模型…
- 已知剩余问题：
- 需要产品/品牌决策：
- 建议下一步：
```

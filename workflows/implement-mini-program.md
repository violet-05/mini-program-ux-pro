# 小程序页面实现工作流

## 前置

- 已有 Master 设计系统，或用户明确只要一个独立组件。
- 已识别技术栈，未擅自迁移框架。
- 已确认页面范围与不改变的业务逻辑。

## 1. 读取实现上下文

1. 读 `design-system/MASTER.md`。
2. 读目标页面的 `pages/<page>.md`（如果存在）。
3. 读项目现有页面、组件、样式 token 和页面注册。
4. 检查现有组件能否复用；优先小范围修改。

## 2. 先结构，后视觉

按页面覆盖文件实现：

1. 页面区域与内容顺序。
2. 导航与返回。
3. 加载、空、错误、权限等状态。
4. 主操作与反馈。
5. 视觉 token。
6. 动效与细节。

不要把“先搭一个漂亮卡片”当作结构设计。

## 3. 按技术栈实现

### 微信原生

- 页面注册在 `app.json`。
- WXML 使用 `view`、`text`、`image`、`button`、`scroll-view` 等。
- 事件用 `bindtap`/`catchtap`，不用 `onclick`。
- 样式使用 WXSS/rpx；不假设所有浏览器 CSS 能力。
- 安全区、胶囊和自定义导航按运行时信息计算。
- 参考 `data/stacks/wechat-native.csv`。

### uni-app

- 页面和 tabBar 配置在 `pages.json`。
- 微信差异使用条件编译；不把 H5 DOM 当小程序。
- 使用 `uni.*` 或按平台封装的 API。
- 检查页面生命周期和编译后的微信样式。
- 参考 `data/stacks/uni-app.csv`。

### Taro

- 页面在 `app.config` 注册。
- 使用 `@tarojs/components` 的 View/Text/Image 等。
- 不把 React Router 或 DOM API 当 Taro 路由/运行环境。
- 检查 px→rpx 的项目配置与编译产物。
- 参考 `data/stacks/taro.csv`。

## 4. 实现关键状态

每个会联网或有输入的页面至少检查：

- 首屏加载与局部加载；
- 空数据与筛选为空；
- 错误、重试、无权限；
- 提交中、防重复；
- 键盘遮挡；
- 固定底栏与安全区；
- 长文本、图片失败；
- 返回后的上下文恢复。

## 5. 组件使用

- 复用 Master 中的组件规范，不复制粘贴多套按钮/卡片。
- 触摸目标至少 88rpx×88rpx。
- 图片有比例、mode 和失败占位。
- 表单标签可见，错误就近。
- 弹窗有明确关闭方式，一次只显示一个关键模态。
- 分享/授权/隐私使用平台真实能力，不伪造成功。

## 6. 代码层自检

```bash
python scripts/audit_mini_program.py --path . --format markdown --fail-on P1
```

注意：

- 这是静态检查，不是编译或真机。
- 先修 P0/P1，再处理 P2/P3。
- 自动检查和规则辅助判断要分开记录。
- 修复后重新运行，确认未引入新问题。

## 7. 构建与验证

### 浏览器

如果项目有 H5 目标或独立 HTML 原型，可以预览布局。必须标注为“浏览器预览”，不能等同于微信小程序。

### 微信开发者工具

1. 导入项目；
2. 编译；
3. 打开目标页面；
4. 走核心路径；
5. 记录控制台错误、截图与基础库版本。

### 真机

至少一台 iOS 和一台 Android，检查：

- 状态栏/胶囊/返回；
- 键盘与安全区；
- 分享、授权、支付；
- 原生组件层级；
- 滚动与低端机性能。

只有实际执行的检查才可以标记通过。

## 8. 交付

- 修改文件清单。
- 设计系统与页面覆盖来源。
- 已执行的检查环境。
- 未执行项与已知风险。
- 需要人工确认的视觉/业务判断。

## 禁止

- 把从网页复制的 HTML/CSS 直接改扩展名冒充小程序实现。
- 未经用户要求重写整个项目或更换框架。
- 用“已优化”掩盖没有验证。
- 删除既有功能只为视觉统一。

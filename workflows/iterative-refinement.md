# 迭代改进工作流

## 目标

在有限轮次内修复高优先级问题，并证明没有破坏现有功能。不是无限“再调好看一点”。

## 默认上限

最多 3 轮。每轮必须有：

1. 当前问题清单；
2. 本轮只处理的问题；
3. 修改范围；
4. 验证方法；
5. 修改前后结果；
6. 新问题检查。

## 第 0 轮：建立基线

```bash
python scripts/audit_mini_program.py --path . --format json --output review-baseline.json
```

同时保存：

- 设计系统版本（若有）；
- 技术栈与页面列表；
- 已执行环境；
- 截图/真机证据（如可提供）；
- 不可改变的业务逻辑。

## 第 1 轮：P0/P1

优先：

- 页面缺失、微信目标不可执行的代码；
- 导航/返回失效；
- 安全区/固定底栏遮挡；
- 键盘遮挡输入或提交；
- 支付/表单重复提交；
- 严重低对比或触摸目标过小；
- 隐私/授权阻断。

修改原则：

- 最小改动；
- 复用现有组件；
- 不重写业务；
- 不替换框架；
- 不用改颜色冒充修复布局。

修改后：

```bash
python scripts/audit_mini_program.py --path . --format json --output review-round1.json
python mpux.py compare review-baseline.json review-round1.json
```

对比基线与本轮问题。只有 `resolved` 是已确认消失的静态问题；`unconfirmed` 需要检查是否漏跑检查或缩小了扫描范围，`new_unverified` 不能直接算作本轮引入的回归。其余仍需人工/运行时验证。

## 第 2 轮：P2

处理：

- 加载/空/错误状态；
- 长文本/长标题；
- token 不一致；
- 组件状态缺失；
- 信息层级与留白；
- 图片比例/失败；
- 深色模式和系统字号。

不要把所有页面同时大改。按核心路径分批，保留回滚点。

## 第 3 轮：P3 与最终复查

只处理：

- 细节对齐；
- 动效/反馈；
- 图标一致性；
- 文案和微交互。

最终复查：

- 重新走核心路径；
- 运行静态工具；
- 检查设计系统与实现一致性；
- 记录修改前后截图/环境；
- 列出仍未解决问题。

## 比较修改前后

至少回答：

- P0/P1 数量是否下降？
- 是否引入新 P0/P1？
- 页面还能否返回、完成核心任务？
- 有没有新增未登记颜色/间距/组件？
- 未验证项是否变化？

静态问题数量下降不等于体验变好；必须结合截图/真机/交互结果。

## 停止条件

停止并交付，当：

- 达到 3 轮；
- P0/P1 已处理或明确阻塞；
- 继续修改会超出用户授权或需要业务决策；
- 环境无法支持进一步验证。

不应以“再调一版”为理由无限循环。

## 最终报告

使用 [交付工作流](final-delivery.md)，必须列出：

- 每轮修改范围；
- 已修复问题；
- 未修复和阻塞；
- 执行/未执行环境；
- 设计系统变化；
- 剩余风险。

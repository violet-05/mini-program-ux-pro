# 页面视觉审查工作流

## 目标

审查页面的视觉层级、排版、密度、对齐、一致性和任务匹配，而不是简单评价“好不好看”。

## 1. 明确环境

在报告开头写明：

- 静态代码 / 浏览器截图 / 微信开发者工具截图 / iOS 真机 / Android 真机；
- 设备尺寸、系统、微信版本、基础库；
- 页面状态（正常、加载、空、错误、键盘、弹层）。

模拟器截图不能代替真机。

## 2. 获取证据

优先顺序：

1. 真实项目运行截图；
2. 微信开发者工具截图（标记工具环境）；
3. 浏览器原型截图（标记为浏览器原型）；
4. 只有代码时，只做结构和规则检查，不评价实际视觉。

截图应覆盖：

- 首屏；
- 页面中部/长内容；
- 页面底部（底栏和安全区）；
- 关键弹层；
- 空/错/加载；
- 长标题、长价格、图片失败。

## 3. 先看任务，再看审美

逐页回答：

- 用户来这里的主要任务是什么？
- 首屏第一眼看到什么？是否与任务一致？
- 主操作是否容易找到？
- 次要信息是否过多？
- 页面是否只是把通用卡片模板换个颜色？

## 4. 视觉维度

### 层级

- 一个视觉焦点；
- 字号、颜色、位置、留白共同形成层级；
- 灰度下仍可分辨；
- 主操作明确。

### 排版

- 正文 28–32rpx，辅助 ≥24rpx；
- 字级数量受控；
- 长标题/长数字规则；
- 中文字体回退可读；
- 系统字号放大不破坏布局。

### 颜色

- 对比度：正文/背景 ≥4.5:1；
- 语义不只靠颜色；
- 品牌色使用克制；
- 深色模式独立验证；
- 图片上文字有底板。

### 布局

- 对齐真实；
- 间距节奏合理；
- 卡片、列表、分区不是同一种容器；
- 留白与信息密度匹配任务；
- 固定在底部的元素不遮挡内容。

### 图片与组件

- 比例统一、不变形；
- 失败占位；
- 图标同源；
- 按钮/输入/标签状态完整；
- 组件换页面仍一致。

## 5. 反模板化检查

- 页面是否只是“搜索框 + 轮播 + 四宫格 + 三卡片”？
- 是否所有区块都圆角卡片＋阴影？
- 是否所有按钮都是胶囊？
- 背景渐变是否有业务理由？
- 风格是否与产品类型和目标用户匹配？
- 是否只换颜色，没有调整布局和层级？

如果命中，先说结构，而不是调色。

## 6. 视觉模型接口（可选）

当前版本未内置视觉模型。若接入，必须通过独立适配器，输入：

```json
{
  "screenshot": "<本地路径>",
  "page_type": "<页面类型>",
  "design_system": "<MASTER.json>",
  "product": "<产品定位>",
  "review_goal": "<视觉审查目标>"
}
```

输出必须是结构化问题，包含：问题、严重度、证据描述、修复建议、置信度。

视觉模型判断与程序测量必须分开：

- 程序：对比度、尺寸、布局溢出、DOM/结构。
- 模型：审美、层级感知、风格匹配，标注置信度。
- 人：业务意图、品牌取舍、最终验收。

没有接入时，不得声称具备“自动审美理解”。

## 7. 输出

每个问题：

```markdown
### [P1] 首屏主任务被活动横幅挤出首屏

- 证据：390×844 截图中，立即购买按钮位于第二屏。
- 影响：用户无法在首屏完成核心任务。
- 建议：将活动区下移，主操作固定在首屏可见区；保留唯一视觉焦点。
- 判断方式：视觉审查 / 人工确认
- 规则：`ux-hierarchy`、`layout-product-detail`
```

## 8. 不得声称

- 未截图却评价具体视觉细节。
- 用开发者工具截图代替真机。
- 把主观喜好写成客观缺陷。
- 只给审美打分，没有可执行修复。
